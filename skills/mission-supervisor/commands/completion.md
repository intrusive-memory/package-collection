# Completion Log Management — COMPLETE_*.md

> **Terminology reminder**: A *mission* is the definable scope of work. A *sortie* is an atomic agent task within that mission.

The supervisor maintains an additive completion log at `$PROJECT_ROOT/COMPLETE_<PROJECT_NAME>.md` that records verified accomplishments in real-time. This provides an independent audit trail and enables final verification when all sorties finish.

**Referenced by**: `commands/execution.md` — called during the event loop after each sortie verification confirms COMPLETED state, and at final completion when all work units are done.

---

## 1. File Initialization

On the first sortie completion, create `COMPLETE_<PROJECT_NAME>.md`:

```markdown
# Completed Work — <Project Name>

Generated by Mission Supervisor
Start: <ISO 8601 timestamp of first dispatch>
Last updated: <ISO 8601 timestamp>

## Terminology

> **Mission** — A definable, testable scope of work. Defines scope, acceptance criteria, and dependency structure.

> **Sortie** — An atomic, testable unit of work executed by a single autonomous AI agent in one dispatch. One aircraft, one mission, one return.

> **Work Unit** — A grouping of sorties (package, component, phase).

## Summary
- Total sorties planned: <N>
- Total sorties completed: 0 (initializing)
- Models used: (none yet)
- Total cost: 0x (relative)
- Total duration: 0 minutes

---

## Work Units
(Sorties will be appended below as they complete)
```

## 2. Recording Sortie Completion

**When**: Immediately after a sortie's verification cascade confirms `COMPLETED` state.

**What to record**: Append a new entry to COMPLETE_*.md with:

```markdown
### ✓ Sortie <N>: <Sortie Name>
- **Work Unit**: <name>
- **Status**: COMPLETED
- **Model**: <haiku|sonnet|opus> (complexity score: <N>)
- **Attempts**: <current>/<max_retries>
- **Timing**:
  - Started: <ISO 8601 dispatch timestamp>
  - Completed: <ISO 8601 completion timestamp>
  - **Duration: <X> minutes** (or hours if >60min)
  - **Turns used: <actual>/<max_turns> (<percentage>% of budget)**
- **Git commits**: <commit_hash>, <commit_hash>, ... (or "none" for non-code sorties)
- **Exit criteria verified**:
  - ✓ <criterion 1 from plan>
  - ✓ <criterion 2 from plan>
  - ...

---
```

**Data sources**:
- **Started timestamp**: From Active Agents table `Dispatched At` column
- **Completed timestamp**: Current time when verification confirms COMPLETED
- **Duration**: `completed_time - started_time`
- **Turns used**: From `TaskOutput` final result (look for turn count in output)
- **Git commits**: `git log --oneline --since="<started_time>" --until="<completed_time>" -- <work_unit_dir>` (first 7 chars of hash only)
- **Exit criteria**: From EXECUTION_PLAN.md for this sortie, mark each as ✓ if verification confirmed it

## 3. Updating Summary Section

After each sortie completion, update the Summary section at the top of COMPLETE_*.md:

```markdown
## Summary
- Total sorties planned: <N>
- Total sorties completed: <count> (in progress)
- Models used: haiku×<count>, sonnet×<count>, opus×<count>
- Total cost: <sum>x (relative: haiku=1x, sonnet=10x, opus=30x)
- Total duration: <sum> minutes (or hours if >60min)
```

**Calculation**:
- Total cost: `(haiku_count × 1) + (sonnet_count × 10) + (opus_count × 30)`
- Total duration: Sum of all sortie durations recorded

## 4. Final Verification (When All Sorties Complete)

**Trigger**: When the last work unit transitions to `COMPLETED` state.

**Process**:

### Step 1: Parse Both Files

1. Read EXECUTION_PLAN.md — extract list of all sorties (IDs, names, exit criteria)
2. Read COMPLETE_*.md — extract list of completed sorties (IDs, names, verified criteria)

### Step 2: Coverage Check

Compare sortie lists:

```markdown
## Final Verification — <timestamp>

### Coverage Check
| Sortie | Planned | Completed | Status |
|--------|---------|-----------|--------|
| Sortie 1 | ✓ | ✓ | VERIFIED |
| Sortie 2 | ✓ | ✓ | VERIFIED |
| Sortie 3 | ✓ | ✗ | MISSING FROM COMPLETION LOG |
| ... | ... | ... | ... |
```

**Check**: Every sortie in EXECUTION_PLAN.md appears in COMPLETE_*.md

### Step 3: Exit Criteria Verification

For each sortie, compare planned exit criteria vs verified criteria:

```markdown
### Exit Criteria Verification
Checking that all planned exit criteria were actually verified...

- Sortie 1: 3/3 criteria verified ✓
- Sortie 2: 4/4 criteria verified ✓
- Sortie 3: 2/3 criteria verified ✗
  - Missing: "Integration tests pass" not verified
- ...

**Result**: ✗ <N> sorties have unverified exit criteria
```

### Step 4: Git Commit Verification

For sorties classified as `code` type:

```markdown
### Git Commit Verification
Checking that code sorties produced commits...

- Sortie 1 (code): 2 commits found ✓
- Sortie 2 (code): 2 commits found ✓
- Sortie 3 (code): 0 commits found ✗
- Sortie 4 (command): N/A (not a code sortie)
- ...

**Result**: ✗ <N> code sorties have no commits
```

### Step 5: Generate Issues Report

```markdown
## Issues Found: <N>

### Issue 1: Sortie 3 missing from completion log
- **Severity**: CRITICAL
- **Details**: Sortie 3 appears in EXECUTION_PLAN.md but has no entry in COMPLETE_*.md
- **Impact**: Cannot verify this sortie was actually completed
- **Recommendation**: Review SUPERVISOR_STATE.md and git history to confirm status

### Issue 2: Sortie 5 missing exit criterion verification
- **Severity**: HIGH
- **Details**: Exit criterion "Integration tests pass" was not verified
- **Recommendation**: Manually run verification command to confirm

<Continue for each issue>
```

### Step 6: Cadence Analysis

Generate comprehensive timing and performance analytics:

```markdown

### Overall Performance
- **Total elapsed time**: <X> hours (<start_timestamp> → <end_timestamp>)
- **Active work time**: <sum of all sortie durations> hours
- **Parallelism efficiency**: <active_time / elapsed_time>%
- **Average sortie duration**: <mean> minutes
- **Sorties per hour**: <total_sorties / elapsed_hours>
- **Total turns used**: <sum> / <total_available> (<percentage>% utilization)

### By Work Unit
| Work Unit | Sorties | Total Time | Avg Time/Sortie | Parallelism Gain |
|-----------|---------|------------|-----------------|------------------|
| <name> | <N> | <sum>h | <avg>min | <calculated>× |
| ... | ... | ... | ... | ... |

**Parallelism calculation**: Compare elapsed time vs sum of work unit durations. If Work Unit A (2h) and Work Unit B (2h) ran in parallel and total elapsed was 2.5h, parallelism gain = (2+2) / 2.5 = 1.6×

**Parallelism saved**: <sequential_time - elapsed_time> hours

### By Model
| Model | Sorties | Avg Duration | Avg Turns | Success Rate | Avg Attempts | Cost Impact |
|-------|---------|--------------|-----------|--------------|--------------|-------------|
| haiku | <N> | <avg>min | <avg> | <first_attempt_success>% | <avg_attempts> | <N>× |
| sonnet | <N> | <avg>min | <avg> | <first_attempt_success>% | <avg_attempts> | <N×10>× |
| opus | <N> | <avg>min | <avg> | <first_attempt_success>% | <avg_attempts> | <N×30>× |

**Success rate**: Sorties completed on first attempt / total sorties for that model
**Avg attempts**: Average retry count (1.0 = all first attempt, 2.0 = one retry on average)

### Velocity Trend
Divide sorties into phases (early, middle, late) and analyze duration trends:

| Sortie <2N/3+1>-<N> | <N> | <avg>min | <"Maintained velocity" / "Slowdown" / etc> |

**Trend**: <✓ Velocity stabilized / ✗ Velocity degraded / ↗ Velocity improved>

### Efficiency Metrics
- **First-attempt success**: <N>/<total> sorties (<percentage>%)
- **Retries required**: <N>/<total> sorties (<percentage>%)
  - <List sorties that required retries with attempt counts>

- **Context budget utilization**: <avg>% avg (<percentage>% headroom)
- **Oversized sorties**: <N> (exceeded 80% of turns budget)
- **Undersized sorties**: <N> (used <15% of turns budget)

### Bottleneck Analysis
**Critical Path**: Sortie <N> → Sortie <M> → ... (<total_duration> total)
**Longest sortie**: Sortie <N> (<name>, <duration>min, <model>)
**Most retries**: Sortie <N> (<attempt_count> attempts)

**Recommendation**: <Analysis of what slowed things down and how to avoid it>

### Estimation Accuracy
Compare estimated turns (from context fitness check) vs actual turns:

| Sortie | Estimated Turns | Actual Turns | Variance | Accuracy |
|--------|----------------|--------------|----------|----------|
| Sortie 1 | <est> | <actual> | <±percentage>% | <✓ Good / ✗ Poor> |

**Accuracy criteria**: ±20% variance = Good, >20% = Poor

**Average estimation error**: ±<percentage>%
**Trend**: <Underestimated/Overestimated> <complex/simple> sorties by <percentage>%

### Time Distribution
Show breakdown of where time was spent:
```

Implementation:     ████████████░░░░ <percentage>% (<hours>h)

```
**Classification**:
- Foundation: Sorties with foundation_score = 1

### Cost Breakdown
```

### Step 7: Final Verdict

```markdown

## Verdict

<If passed>:

<If failed>:
```
